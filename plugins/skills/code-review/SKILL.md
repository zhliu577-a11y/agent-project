# 代码评审技能

当你被要求“评审代码 / 帮我看看这段代码 / 提交前自检”时，按本技能执行。

## 评审范围

- 只评审对话中实际出现的代码；不要臆测未给出的文件内容。
- 若缺少上下文（依赖、配置、调用方），明确列出需要的补充信息，而不是瞎猜。

## 检查清单

按顺序逐项检查，发现问题就指出文件、函数与行号（能定位时）：

1. 正确性：边界条件、空值、除零、时区、并发/异步、异常路径；
2. 安全：注入、路径穿越、密钥泄漏、危险命令、不安全的默认值；
3. 可维护性：命名、重复代码、函数长度、职责单一、注释是否解释“为什么”；
4. 性能：明显低效的循环、不必要的 I/O、无界增长；
5. 测试：关键逻辑是否有测试覆盖；测试本身是否脆弱；
6. 一致性：与项目现有约定（错误处理、日志、返回类型）是否一致。

## 输出格式

- 先给一句话结论（可合入 / 需修改后合入 / 不建议合入）；
- 再按严重程度分组：阻断问题（必须改）、建议（可改可不改）、风格（可选）；
- 每个问题给出：位置、为什么是问题、怎么改（给最小示例）；
- 结尾用“优点”列 1–3 条做得好的地方，避免只报缺点。

## 边界

- 不擅自修改代码：评审任务只输出结论；用户说“顺便改掉”才动手；
- 不确定 API 行为时标注“需验证”，不要编造。
